# AQP Balancer — адаптивный балансировщик аналитических запросов

Адаптивный балансировщик аналитических запросов: приближённое выполнение,
детектирование фазовых переходов распределения задержек и обучение стратегий
выборки.

Балансировщик можно запускать как самостоятельный сервис: он не зависит от
каталогов `backends` и `clients`, не читает демонстрационный датасет и работает
с любым HTTP-бэкендом, который реализует описанный ниже контракт.

Проект также содержит демонстрационный стенд:

- балансировщик принимает запросы клиентов, выбирает сервер, управляет активным
  набором узлов и отсекает избыточную нагрузку;
- каждый бекенд реально выполняет запрос по выбранной стратегии (`EXACT`,
  `UNIFORM`, `STRATIFIED`), но моделирует задержку, конкуренцию за воркеры и
  отказы так, как это делал бы настоящий аналитический движок;
- клиенты нагрузки работают как внешние независимые процессы и не входят в
  состав балансировщика.

> **Режимы запуска.** Итоговый JAR лежит в корне репозитория:
> `adaptive-query-balancer.jar`. Обычный запуск `java -jar
> adaptive-query-balancer.jar` включает standalone-режим: demo-эндпоинты,
> simulated-серверы и discovery выключены. Для локальной демонстрации
> используйте `../start-demo.sh` из этой папки или `./start-demo.sh` из корня.

Основная идея: балансировщик не просто распределяет запросы, а одновременно
решает две задачи — **где** выполнить запрос и **как** его выполнить. Выбор
сервера зависит от текущей загрузки и ёмкости, а выбор стратегии — от оценённой
тяжести хвоста распределения задержек.

## Что демонстрирует проект

- **Active set** — в ротации находится только то число серверов, которое нужно
  текущей нагрузке. Остальные остаются подключёнными в режиме standby,
  проходят health-check и готовы к немедленному включению.
- **Load-aware routing** — запрос уходит на активный сервер с минимальной
  прогнозируемой утилизацией, а не по «слепому» round-robin.
- **Admission control** — при перегрузке запросы отсекаются с явным ответом
  `429`, не доводя бекенды до коллапса очередей.
- **Приближённое выполнение** — `EXACT`, `UNIFORM` и `STRATIFIED` дают разный
  компромисс между точностью и задержкой.
- **Детектирование фаз** — по хвосту распределения задержек оценивается α
  (индекс тяжёлого хвоста), а EWS и CUSUM помогают заметить переход заранее.
- **Обучение стратегий** — контекстуальный Thompson Sampling выбирает стратегию
  с учётом текущего диапазона α и награды за точность/скорость.
- **Наблюдаемость** — веб-интерфейс и SSE-поток показывают нагрузку, метрики
  адаптивного контура, состояние пула и последние запросы.

## Требования

- JDK 17 или новее.
- Bash и `curl` для скриптов запуска. На Windows удобнее использовать WSL;
  сами Java-приложения от Bash не зависят.
- Свободные порты `8080` и `9001–9005`.
- Maven устанавливать не обязательно: в `adaptive-query-balancer` и `backends`
  есть Maven Wrapper (`./mvnw`).
- При первой сборке нужен доступ к Maven Central или заранее заполненный
  локальный кэш Maven. Клиенты собираются обычным `javac` и внешних
  зависимостей не требуют.

## Быстрый старт: standalone-балансировщик

Для реального проекта нужен только каталог `adaptive-query-balancer`.

Если итоговый JAR уже собран, он лежит в корне репозитория:

```bash
java -jar ../adaptive-query-balancer.jar
```

Сборка из исходников:

```bash
cd adaptive-query-balancer
./mvnw -q clean package -DskipTests
java -jar target/adaptive-query-balancer-1.0.0.jar
```

По умолчанию сервис слушает `127.0.0.1:8080`, не подключает ни одного сервера,
не сканирует сеть и не включает demo-endpoint'ы. Подключите свой HTTP-бэкенд:

```bash
curl -X POST http://localhost:8080/api/servers \
  -H "Content-Type: application/json" \
  -d '{
    "name": "analytics-1",
    "url": "http://backend-host:9001/execute",
    "healthUrl": "http://backend-host:9001/health",
    "statsUrl": "http://backend-host:9001/stats",
    "healthMethod": "GET",
    "headers": {"Authorization": "Bearer env:BACKEND_TOKEN"},
    "capacity": 32,
    "timeoutMs": 5000
  }'
```

Запросы отправляются на `POST /api/execute`. Readiness и метрики доступны через
`/actuator/health/readiness` и `/actuator/prometheus`. Для доступа к admin-API
из не-loopback адреса задайте `BALANCER_ADMIN_TOKEN` и передавайте его в
заголовке `X-Admin-Token` или как `Authorization: Bearer ...`.

```bash
curl -X POST http://localhost:8080/api/execute \
  -H "Content-Type: application/json" \
  -d '{"clientId":"demo","requestId":"r-1","sql":"SELECT avg(value) FROM events","type":"AGGREGATE","estimatedRows":1000}'
```

Если бэкенд не отдаёт `exactResult`/`relativeError` и не помечает ответ как
точный, поле `relativeError` в ответе будет `null`, а обучение стратегий
оптимизирует только задержку. Это штатный режим для произвольных бэкендов.


`backends/logs/server-*.log`.

### 2. Подключить серверы

Если вы запускали `start-demo.sh`, discovery уже выполнен и серверы должны быть
в списке. Иначе откройте раздел **«Серверы»** и нажмите **«Найти серверы»**.

discovery по умолчанию выключен: серверы подключаются вручную или через

То же самое через API:

```bash
curl -X POST http://localhost:8080/api/servers/discover
```

Серверы получают автоматические идентификаторы `server-1`, `server-2`, ….
Отображаемое имя берётся из поля `name` (для ручного добавления) или из `/info`
(для discovery); если имя не задано, используется «Сервер №N». Нумерация
продолжает сохранённый `nextSequence`.

Файл подключений по умолчанию — `./data/connected-servers.json` относительно
рабочей директории. Путь можно переопределить через `BALANCER_SERVERS_FILE` или
`balancer.servers-file`; в поставку не входит предзаполненный файл.

Или нажмите **«Сбросить метрики»** в интерфейсе.

Если демо запущено через корневой скрипт:

## Как проходит запрос

1. Клиент отправляет JSON на `POST /api/execute`.
2. Балансировщик нормализует запрос: подставляет значения по умолчанию,
   ограничивает `estimatedRows`, `skewness` и приводит тип к `QueryType`.
3. `AdmissionController` проверяет наличие маршрутизируемых серверов, при
   необходимости расширяет активный набор, резервирует слот `inFlight` и
   сравнивает загрузку с допустимым пределом.
4. Если запрос принят, `ActiveServerPool` выбирает активный сервер с минимальной
   прогнозируемой утилизацией.
5. `LoadBalancerCore` использует последнюю оценку α и фазы, определяет
   допустимые стратегии и выбирает стратегию через Thompson Sampling. Тяжёлый
   пересчёт α выполняется не на каждом запросе, а по таймеру/после пачки
   успешных выборок.
6. Балансировщик отправляет запрос на выбранный бекенд: `POST /execute` с
   выбранной стратегией и текущей фазой.
7. Бекенд выполняет выборку по своему набору данных, моделирует задержку,
   конкуренцию и возможный отказ и возвращает результат.
8. Если бекенд вернул `relativeError` или `exactResult`, `AccuracyProvider`
   вычисляет относительную ошибку. Иначе ошибка считается неизвестной, и
   reward оптимизирует только задержку. Затем обновляется Beta-оценка стратегии,
   а успешная задержка попадает в скользящее окно.
9. Клиент получает ответ с результатом, стратегией, фазой, задержкой и текущим
   уровнем нагрузки.

Важно, что маршрутизация и адаптивная выборка — два независимых контура.
Утилизация влияет на выбор сервера и admission control, а α и фаза — только на
выбор стратегии выполнения.

## Маршрутизация и активный набор

### Состояния сервера

- **disabled** — сервер отключён вручную и не участвует в маршрутизации.
- **unhealthy** — последняя проверка `/health` завершилась ошибкой или кодом
  `5xx`.
- **routable** — сервер включён и не провалил последнюю проверку. Сервер, у
  которого проверка ещё не выполнялась, считается доступным оптимистично.
- **active** — сервер находится в текущем активном наборе и может получать
  запросы.
- **standby** — сервер подключён, проходит health-check и опрос `/stats`, но
  запросов не получает, пока его не активирует контроллер.

### Как выбирается сервер

Для каждого активного сервера считается прогнозируемая утилизация:

```text
projectedUtilization = (active + queued + 1) / effectiveCapacity
```

Где `active` и `queued` — живые счётчики бекенда из `/stats`, а
`effectiveCapacity` — свежая ёмкость из `/stats`, если данные не старше
10 секунд, иначе настроенная ёмкость сервера.

Выбирается сервер с минимальным `projectedUtilization`. При равенстве
предпочтение получает сервер с большей ёмкостью, затем с большим весом, затем
с меньшим идентификатором.

### Scale-out

По умолчанию активен один сервер. Перед приёмом каждого запроса контроллер
проверяет:

- агрегированную утилизацию активного набора;
- прогнозируемую утилизацию самого загруженного активного сервера.

Если хотя бы один показатель превышает
`balancer.active-set.scale-out-utilization` (по умолчанию `0.70`), из standby
активируется лучший сервер — с минимальной прогнозируемой утилизацией и
наибольшей ёмкостью.

### Scale-in

Раз в `balancer.active-set.tick-ms` (по умолчанию 3 секунды) контроллер
проверяет возможность вернуть лишний сервер в standby. Для этого нужно:

- иметь больше серверов, чем `balancer.active-set.min-size`;
- держать агрегированную утилизацию ниже
  `balancer.active-set.scale-in-utilization` (по умолчанию `0.25`) непрерывно
  в течение `balancer.active-set.scale-in-cooldown-ms` (по умолчанию 15 секунд);
- иметь активный сервер с нулевыми `active` и `queued`;
- чтобы утилизация оставшихся серверов после удаления не превысила порог
  scale-out.

Из подходящих серверов удаляется наименее ёмкий, чтобы не терять
производительность кластера.

### Health-check

- Период: `balancer.health-check.interval-ms`, по умолчанию 15 секунд.
- Первая проверка: через `balancer.health-check.initial-delay-ms`, по умолчанию
  3 секунды.
- Метод: `GET /health` по умолчанию; можно задать `HEAD` или отдельный
  `healthUrl`/`healthMethod` на сервере.
- При `405`/`501` на `GET` выполняется fallback на `HEAD`.
- Здоровым считается только ответ `2xx`; таймаут по умолчанию 2 секунды.
- Если сервер стал недоступен, он автоматически исключается из активного
  набора. При восстановлении `/health` он снова может быть выбран.
- Standby-серверы продолжают проверяться, поэтому переключение не требует
  повторного discovery.

### Параметры active set

```properties
balancer.active-set.min-size=1
balancer.active-set.scale-out-utilization=0.70
balancer.active-set.scale-in-utilization=0.25
balancer.active-set.scale-in-cooldown-ms=15000
balancer.active-set.tick-ms=3000
```

## Admission control и перегрузка

Admission control защищает и балансировщик, и бекенды от одновременного
наплыва запросов.

- Ёмкость кластера равна сумме `effectiveCapacity` активных маршрутизируемых
  серверов.
- Каждый принятый запрос занимает один слот `inFlight`.
- Если `inFlight` превышает `ceil(capacity × overload-factor)`, запрос не
  отправляется на бекенд и получает `429`.

Уровни нагрузки в ответах и мониторинге:

| Уровень | Условие | Смысл |
|---|---|---|
| `NORMAL` | утилизация ниже 70% | кластер работает штатно |
| `WARNING` | утилизация от 70% до 90% | запас ёмкости заканчивается |
| `OVERLOAD` | утилизация 90% и выше | кластер перегружен; отсечение начинается при превышении 120% ёмкости |

Если подключённых серверов нет или все они недоступны, снимок мониторинга
показывает `OVERLOAD` и предупреждение с причиной, а `POST /api/execute`
возвращает `503 NO_SERVERS`.

Причины ответов для клиента:

| HTTP | `status` | Когда возникает |
|---:|---|---|
| `200` | `OK` | запрос выполнен |
| `429` | `SHED` | admission control отсек запрос; в ответе есть `Retry-After: 1` |
| `503` | `NO_SERVERS` | нет включённых или доступных серверов |
| `502` | `FAILED` | бекенд вернул ошибку, превысил таймаут или недоступен |
| `500` | другое | непредвиденная ошибка обработки |

Пример ответа при перегрузке:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
Content-Type: application/json

{
  "requestId": "client-3-91234",
  "status": "SHED",
  "loadLevel": "OVERLOAD",
  "message": "Все серверы перегружены: 155 из 154 слотов"
}
```

Бекенды имеют собственные ограниченные очереди. Если очередь переполнена,
бекенд отвечает `429`; при смоделированном отказе — `503`. Для клиента такие
ответы бекенда выглядят как `FAILED` от балансировщика (`502`), потому что
балансировщик не повторяет запрос автоматически.

Параметры:

```properties
balancer.admission.warning-utilization=0.70
balancer.admission.critical-utilization=0.90
balancer.admission.overload-factor=1.20
```

## Адаптивный контур

Адаптивный контур не влияет на выбор сервера. Он определяет, насколько
агрессивную стратегию выборки можно применить к следующему запросу.

### Скользящее окно задержек

- Хранится до 1000 последних **успешных** задержек.
- Ошибки и отсечённые запросы в окно не попадают.
- Оценка α запускается только после накопления 20 значений.
- Пока данных недостаточно, используется α по умолчанию `2.5`. Детектору нужно
  ещё минимум 8 сглаженных оценок α, чтобы выйти из фазы `UNKNOWN`.
- Тяжёлый пересчёт α не выполняется на каждом запросе: он запускается не чаще
  `balancer.adaptive.refresh-interval-ms` или после
  `balancer.adaptive.refresh-sample-interval` успешных выборок. Размер окна,
  минимум выборок, пороги детектора и веса reward настраиваются.

### Оценка α

Используется ансамбль из трёх оценщиков индекса хвоста:

| Оценщик | Идея |
|---|---|
| Hill | оценивает показатель по логарифмам верхних порядковых статистик |
| Pickands | сравнивает верхние квантили распределения |
| Dekkers–Eenmaas (moments) | оценивает форму хвоста через моменты превышений порога |

Итоговая α — медиана доступных оценок. Если часть оценщиков не смогла
посчитать значение на текущей выборке, ансамбль использует первую валидную
оценку вместо медианы. Это делает контур устойчивым к вырожденным выборкам.

Оценка α сглаживается:

```text
smoothedAlpha = 0.7 × previousAlpha + 0.3 × currentAlpha
```

### Фазы и раннее предупреждение

Детектор хранит до 120 сглаженных значений α и классифицирует фазу после
накопления минимум 8 значений.

EWS (Early Warning Score) учитывает:

- тренд α;
- автокорреляцию первого порядка;
- отношение короткой и длинной дисперсий;
- частоту пересечений уровня α = 2.0.

```text
EWS = 0.4 × trend + 0.3 × rho1 + 0.2 × varianceRatio + 0.1 × crossingFrequency
```

CUSUM реагирует на устойчивое смещение α вниз:

```text
cusum = max(0, cusum + (2.2 - smoothedAlpha) - 0.05)
```

Классификация фазы:

| Фаза | Условие |
|---|---|
| `UNKNOWN` | недостаточно успешных задержек или оценок α |
| `HEAVY_TAIL` | сглаженная α ≤ 2.0 |
| `WARNING` | 2.0 < сглаженная α ≤ 2.2, либо 2.2 < α ≤ 2.25 при `EWS > 0.6` или `CUSUM > 1.0` |
| `LIGHT_TAIL` | α > 2.2 и не сработало раннее предупреждение |

### Стратегии выполнения

| Стратегия | Что делает | Особенности |
|---|---|---|
| `EXACT` | обрабатывает все 30 000 строк эталонного набора | максимальная точность, наибольшая задержка |
| `UNIFORM` | случайная выборка размером до 10 000 строк | быстрее, но возможна заметная ошибка на тяжёлом хвосте |
| `STRATIFIED` | пропорциональная выборка по стратам набора | компромисс между точностью и скоростью |

Политика допустимых стратегий:

| Фаза / α | Разрешённые стратегии |
|---|---|
| `UNKNOWN` | `EXACT`, `UNIFORM`, `STRATIFIED` |
| `HEAVY_TAIL` или α ≤ 2.0 | `UNIFORM`, `STRATIFIED` |
| `WARNING` или α ≤ 2.2 | `UNIFORM`, `STRATIFIED` |
| `LIGHT_TAIL` | `EXACT`, `UNIFORM` |

Политика использует текущую фазу детектора и последнюю несглаженную оценку α.
Таким образом, при тяжёлом хвосте стратегия `EXACT` запрещена, а в лёгком
хвосте запрещена `STRATIFIED`, которая в этой фазе не даёт выигрыша по
сравнению с более простыми вариантами.

### Thompson Sampling

Для каждой разрешённой стратегии хранится Beta-распределение `Beta(1, 1)`.
Перед выполнением запроса сэмплируется значение из каждого разрешённого
распределения, и выбирается стратегия с максимальным сэмплом. После успешного
выполнения параметры обновляются:

```text
alpha += reward
beta  += 1 - reward
```

Награда:

```text
reward = 0.7 × (1 - relativeError) - 0.3 × min(1, latencyMs / 10000)
```

Если `relativeError` неизвестен:

```text
reward = 1 - min(1, latencyMs / 10000)
```

Итоговый reward ограничивается диапазоном `[0, 1]`. Веса задаются через
`balancer.adaptive.reward-accuracy-weight`, `reward-latency-weight` и
`reward-latency-scale-ms`.

- Относительная ошибка берётся из ответа бекенда (`relativeError` или
  `exactResult`); собственного эталонного датасета у балансировщика нет.
- Если стратегия `EXACT` вернула точный результат, ошибка считается нулевой.
- Ошибка ограничивается сверху единицей.
- При неуспешном выполнении обновление Beta-оценки не производится.
- Контекст запроса включает диапазон α, тип запроса, skewness, час суток и
  загрузку платформы. В текущей реализации ключом контекста служит только
  диапазон α: именно для него ведутся отдельные Beta-оценки стратегий.

### `POST /api/execute`

Основной endpoint для внешних клиентов.

Поля запроса:

| Поле | Тип | Обязательное | По умолчанию | Примечание |
|---|---|---:|---|---|
| `clientId` | string | нет | — | идентификатор клиента; передаётся бэкенду и доступен в его логах |
| `requestId` | string | нет | `req-N` | идентификатор запроса в ответе и логах |

```json
{
```

```json
  "result": 89.4631,

  "loadLevel": "NORMAL",

  "capacity": 48,

}
```

Поля ответа:

| Поле | Значение |
|---|---|
| `requestId` | идентификатор запроса |
| `status` | `OK`, `SHED`, `NO_SERVERS` или `FAILED` |
| `serverId` | технический идентификатор сервера |

### Мониторинг

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/monitor/snapshot` | один полный снимок состояния |
| `GET` | `/api/monitor/stream?intervalMs=1000` | SSE-поток снимков |
| `POST` | `/api/monitor/reset` | сброс метрик и адаптивного состояния |

SSE-поток не генерирует запросы к бекендам. Интервал ограничивается диапазоном
`200…5000` мс. Каждое событие имеет имя `snapshot` и содержит JSON снимка.

Снимок включает:

- счётчики `offeredCount`, `acceptedCount`, `completedCount`, `successCount`,
  `failedCount`, `shedCount`;
- текущую нагрузку: `inFlight`, `utilization`, `loadLevel`, `activeServers`,
  `totalServers`, `totalCapacity`, `warning`;
- адаптивные значения: `estimatedAlpha`, `smoothedAlpha`, `phase`, `ews`,
  `cusum`, `windowSize`;
- задержки: `averageLatency`, `latencyP50`, `latencyP95`, `latencyP99`,
  `minLatency`, `maxLatency`;
- распределения стратегий, фаз и типов запросов;
- статистику каждого сервера: состояние `ACTIVE`/`STANDBY`, ёмкость,
  прогнозируемую утилизацию, очередь, отказы, доступность и последнюю ошибку;
- последние 20 запросов со статусами `OK`, `SHED` или `FAILED`;
- `elapsedMs` — время с последнего сброса метрик.

`POST /api/monitor/reset` очищает счётчики, скользящее окно задержек, детектор
фаз, admission control, active set и серверную статистику. Подключения
серверов и накопленные Beta-оценки стратегий при этом сохраняются.

### Управление серверами

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/servers` | список подключённых серверов и их статистика |
| `POST` | `/api/servers/discover` | поиск серверов в настроенном диапазоне |
| `POST` | `/api/servers` | ручное подключение сервера |
| `PUT` | `/api/servers/{id}` | изменение настроек сервера |
| `POST` | `/api/servers/{id}/check` | немедленная проверка `/health` |
| `DELETE` | `/api/servers/{id}` | удаление сервера |

Список:

```bash
curl http://localhost:8080/api/servers
```

Discovery:

```bash
curl -X POST http://localhost:8080/api/servers/discover
```

Ответ discovery содержит три массива: `added`, `existing` и `unreachable`.
Новый сервер добавляется только если его `/info` ответил и вернул непустой
`serverId`. Повторно найденный URL не дублируется. Недоступные адреса
попадают в `unreachable` с причиной.

Ручное добавление:

```bash
curl -X POST http://localhost:8080/api/servers \
  -H "Content-Type: application/json" \
  -d '{
    "type": "HTTP",
    "url": "http://127.0.0.1:9011/execute",
    "weight": 10,
    "capacity": 32,
    "enabled": true,
    "timeoutMs": 10000
  }'
```

После добавления или изменения сервера балансировщик сразу выполняет проверку
доступности, не дожидаясь очередного планового health-check.

Поля:

| Поле | По умолчанию | Примечание |
|---|---|---|
| `name` | `server` | отображаемое имя; если не задано, используется «Сервер №N» |
| `type` | `HTTP` | `HTTP`; `SIMULATED` доступен только в demo-режиме |
| `url` | — | обязателен для `HTTP`; полный URL execute-endpoint'а |
| `healthUrl` | производный | опциональный полный URL health-endpoint'а |
| `statsUrl` | производный | опциональный полный URL stats-endpoint'а |
| `healthMethod` | `GET` | `GET` или `HEAD`; при `405`/`501` для `GET` выполняется fallback на `HEAD` |
| `headers` | `{}` | дополнительные заголовки; значения `env:VAR` берутся из окружения |
| `weight` | `10` | используется при выборе сервера как дополнительный критерий |
| `capacity` | `32` | ёмкость до получения свежего `/stats` |
| `enabled` | `true` | выключенный сервер не участвует в маршрутизации |
| `timeoutMs` | `3000` | таймаут HTTP-запроса, `100…60000` мс |
| `baseLatencyMs` | `40` | используется только для `SIMULATED` |
| `failureRate` | `0` | используется только для `SIMULATED` |

Обновление:

```bash
curl -X PUT http://localhost:8080/api/servers/server-1 \
  -H "Content-Type: application/json" \
  -d '{"capacity": 64, "timeoutMs": 15000}'
```

Отсутствующие в `PUT` поля сохраняют текущие значения.

Проверка доступности:

```bash
curl -X POST http://localhost:8080/api/servers/server-1/check
```

Удаление:

```bash
curl -X DELETE http://localhost:8080/api/servers/server-1
```

HTTP-серверы с одинаковым URL повторно не добавляются. Некорректный URL или
неизвестный идентификатор возвращают `400` или `404` с JSON-описанием ошибки.

### Совместимый контракт бекенда

Балансировщик не ограничен встроенными пятью серверами. Подключить можно любой
HTTP-сервер, который:

- принимает `POST` на настроенный execute-URL с JSON;
- возвращает `2xx` и JSON со `status: "OK"` и числовым `result`;
- отдаёт health-endpoint с кодом `2xx` (по умолчанию `GET /health`);
- опционально отдаёт `/info` с `serverId`, `name`, `capacity` для discovery;
- опционально отдаёт `/stats` с полями `active`, `queued`, `capacity`,
  `queueCapacity`, `rejectedRequests`, `utilization`;
- опционально возвращает `exactResult` (точный агрегат) или `relativeError`,
  чтобы балансировщик мог оценивать точность и обучать стратегии.

Пример успешного ответа:

```json
{
  "status": "OK",
  "result": 89.4631,
  "exactResult": 95.2,
  "sampleSize": 1000,
  "totalRows": 30000,
  "approximate": true
}
```

Если `/stats` недоступен или данные устарели (TTL 10 секунд), балансировщик
использует настроенную ёмкость и локальные счётчики отправленных запросов.
Health-endpoint'ы и stats-endpoint'ы можно задать явно или вывести из execute-
URL; для сервисов с path-префиксом используйте явные `healthUrl`/`statsUrl`.

### Служебные endpoint'ы симуляции

Эти endpoint'ы доступны только при `balancer.demo.enabled=true` и не проходят
через admission control и active set:

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/simulate` | пакетная симуляция с параметрами `totalQueries`, `seed`, `alpha` |
| `GET` | `/api/stream?seed=42&alpha=2.5&batchSize=25&intervalMs=500` | SSE-поток симуляции |

Для повседневной работы используйте `POST /api/execute`: он отражает реальный
контур балансировщика.

## Веб-интерфейс

Интерфейс доступен по адресу <http://localhost:8080> и состоит из двух
разделов.

### «Мониторинг»

- Подключается к `/api/monitor/stream` и обновляет данные раз в секунду.
- Показывает уровень нагрузки и предупреждение о перегрузке.
- Отображает счётчики предложенных, принятых, завершённых и отсечённых
  запросов, текущий RPS, `inFlight`, ёмкость и утилизацию.
- Показывает α, сглаженную α, фазу, EWS и CUSUM.
- Строит график задержек и показывает p50/p95/p99, минимум и максимум.
- Показывает распределения стратегий, фаз и типов запросов.
- Показывает таблицу серверов с состояниями `ACTIVE`/`STANDBY`.
- Показывает последние запросы с результатом, стратегией и фазой.
- Кнопка «Сбросить метрики» вызывает `/api/monitor/reset`.

### «Серверы»

- Список подключённых серверов с URL, ёмкостью, запросами, ошибками,
  утилизацией, состоянием пула и доступностью.
- Кнопка «Найти серверы» запускает discovery.
- Кнопка «Добавить сервер» открывает форму ручного подключения.
- Для существующего сервера доступны редактирование, проверка и удаление.
- Подключения автоматически сохраняются в `data/connected-servers.json`.

Веб-интерфейс не является административной панелью с разграничением прав.
Не выставляйте балансировщик в публичную сеть без внешней аутентификации.

## Клиенты нагрузки

Клиенты — самостоятельные Java-приложения без внешних зависимостей. Каждый
клиент генерирует SQL-подобные запросы, JSON и отправляет их на
`POST /api/execute`.

| Клиент | Rate | Concurrency | Seed | Назначение |
|---|---:|---:|---:|---|
| `client-1` | 30 rps | 4 | 101 | лёгкая фоновая нагрузка, проверка работоспособности |
| `client-2` | 300 rps | 32 | 202 | средняя нагрузка, демонстрация scale-out |
| `client-3` | 2000 rps | 160 | 303 | стресс-тест, перегрузка и shedding |

Профиль генерируемых запросов:

- `SCAN` — 40%;
- `JOIN` — 25%;
- `AGGREGATE` — 25%;
- `TOP_K` — 5%;
- `UNKNOWN` — 5%;
- `estimatedRows` — логнормальное распределение в диапазоне `1 000…1 000 000`;
- `skewness` — равномерное распределение `0…1`;
- `arrivalTimeMs` — текущее время.

Параметры командной строки:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--url` | `http://127.0.0.1:8080/api/execute` | адрес балансировщика |
| `--client-id` | `client` | идентификатор клиента в запросах и логах |
| `--rate` | `20` | целевое число запросов в секунду на весь клиент; `0` — без ограничения |
| `--concurrency` | `4` | число рабочих потоков |
| `--seed` | `1` | seed генератора запросов |
| `--duration` | `0` | длительность в секундах; `0` — до остановки |
| `--max-requests` | `0` | остановиться после N предложенных запросов; `0` — без ограничения |
| `--timeout-ms` | `10000` | таймаут HTTP-запроса |
| `--help` | — | показать справку |

Примеры:

```bash
clients/client-2/run.sh --rate 500 --concurrency 64 --duration 120
clients/client-3/run.sh --max-requests 100000 --timeout-ms 15000
clients/client-1/run.sh --url http://127.0.0.1:8080/api/execute
```

Полная справка:

```bash
java -cp clients/target/classes com.mullagaliev.aqpclient.LoadClient --help
```

Статистика печатается каждые 2 секунды:

```text
[client-3] offered=1748 (518 rps) ok=1505 shed=84 failed=3 clientErr=0 inFlight=156 avg=380.8ms max=1907.4ms
```

Классификация ответов:

| Ответ | Что означает |
|---|---|
| `2xx` | запрос выполнен (`ok`) |
| `429` | запрос отсечён балансировщиком (`shed`) |
| `5xx` | ошибка бекенда или отсутствие серверов (`failed`) |
| прочие `3xx`/`4xx` | неожиданный ответ (`clientErr`) |
| сетевая ошибка или таймаут | `clientErr` |

`--rate` задаёт суммарный темп, а не темп каждого потока. При `rate > 0`
каждый воркер выдерживает паузу `concurrency / rate` секунды между запросами,
поэтому фактический RPS может быть ниже целевого, если бекенды не успевают
отвечать.

Пять бекендов запускаются как отдельные Spring Boot-процессы. Каждый узел

| Сервер | Порт | Ёмкость | Очередь | Базовая задержка | α | Ошибки | Профиль |
|---|---:|---:|---:|---:|---:|---:|---|
| `server-1` | 9001 | 32 | 64 | 2.5 мс | 2.7 | 0.05% | `fast-nvme` |
| `server-2` | 9002 | 24 | 48 | 5.0 мс | 2.25 | 0.2% | `balanced` |
| `server-3` | 9003 | 16 | 32 | 8.0 мс | 1.75 | 0.5% | `heavy-tail-storage` |
| `server-4` | 9004 | 48 | 96 | 3.5 мс | 2.4 | 0.1% | `memory-optimized` |
| `server-5` | 9005 | 8 | 16 | 14.0 мс | 1.55 | 2.0% | `legacy-overloaded` |

Дополнительные параметры производительности:

| Сервер | мс на 1000 строк | Коэффициент конкуренции |
|---|---:|---:|
| `server-1` | 0.08 | 0.30 |
| `server-2` | 0.12 | 0.40 |
| `server-3` | 0.20 | 0.55 |
| `server-4` | 0.05 | 0.25 |
| `server-5` | 0.35 | 0.80 |

Каждый узел:

- хранит копию набора из 30 000 строк;
- реально выполняет `EXACT`, `UNIFORM` или `STRATIFIED` через `SamplingEngine`;
- для `TOP_K` агрегирует максимум, для остальных типов запросов — среднее;
- для `UNIFORM` и `STRATIFIED` берёт выборку размером
  `min(estimatedRows, 10 000)`;
- имеет ограниченный пул воркеров и ограниченную очередь;
- оценивает задержку по базовой стоимости, стоимости на строку и конкуренции;
- добавляет к задержке тяжёлый Pareto-хвост с параметром α;
- возвращает `429`, если очередь переполнена;
- случайно отказывает согласно `failure-rate`;
- пишет строку в лог на каждый запрос;
- отдаёт живую нагрузку через `/stats`.

Упрощённо моделируемая задержка выглядит так:

```text
scale = (baseLatencyMs + rowsScanned / 1000 × msPerThousandRows)
      × (1 + contentionFactor × active / capacity)

latency = scale / (1 - U)^(1 / alpha)
```

Где `U` — случайное число из `[0, 1)`. Результат ограничивается диапазоном
от 0.5 мс до 60 секунд.

### API бекенда

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/execute` | выполнить запрос |
| `GET`, `HEAD` | `/health` | проверить доступность |
| `GET` | `/info` | метаданные, ёмкость и профиль |
| `GET` | `/stats` | активные, ожидающие, ёмкость и отказы |
| `PUT` | `/admin/profile` | изменить α, задержку, ошибки и конкуренцию |
| `POST` | `/admin/reset` | сбросить серверные счётчики |

Запрос к `/execute`:

```json
{
  "id": "client-2-42",
  "sql": "SELECT ...",
  "estimatedRows": 150000,
  "type": "AGGREGATE",
  "skewness": 0.73,
  "arrivalTimeMs": 1795080000000,
  "strategy": "STRATIFIED",
  "phase": "WARNING",
  "clientId": "aqp-balancer"
}
```

`strategy` по умолчанию равен `EXACT`. Неизвестная стратегия возвращает `400`.
Успешный ответ содержит `status`, `result`, `exactResult`, `sampleSize`,
`totalRows`, `strategy`, `executionTimeMs`, `queueWaitMs`, `capacity`,
`queueCapacity`, `active`, `queued` и `utilization`. `exactResult` добавлен для
демонстрации необязательного контракта точности; сторонний бэкенд может
возвращать вместо него `relativeError` или не возвращать ни то, ни другое.

`GET /info` отдаёт `serverId`, `name`, `version`, `profile`, `capacity`,
`queueCapacity`, `datasetRows`, `strategies`, `baseLatencyMs`, `alpha`,
`failureRate`, `msPerThousandRows` и `contentionFactor`.

`GET /stats` отдаёт счётчики принятых, завершённых и отсечённых запросов,
успехи и ошибки, среднее время обслуживания, среднее ожидание в очереди,
`active`, `queued`, `capacity`, `queueCapacity` и `utilization`.

### Изменение профиля в рантайме

Это удобный способ продемонстрировать фазовый переход без перезапуска узлов:

```bash
curl -X PUT http://127.0.0.1:9005/admin/profile \
  -H "Content-Type: application/json" \
  -d '{
    "alpha": 1.3,
    "baseLatencyMs": 60,
    "failureRate": 0.05,
    "msPerThousandRows": 1.0,
    "contentionFactor": 1.2
  }'
```

Допустимые значения:

- `alpha`: `1.05…10`;
- `baseLatencyMs`: положительное значение до `60000`;
- `failureRate`: `0…1`;
- `msPerThousandRows`: `0…1000`;
- `contentionFactor`: `0…10`;
- `logRequests`: `true` или `false`.

`POST /admin/reset` сбрасывает только статистику сервера. Профиль и накопленное
состояние пула воркеров не меняются.

### Добавление своих бекендов

Discovery выключен по умолчанию. В demo-профиле он сканирует
`127.0.0.1:9001…9010`. Для реального окружения включайте его явно и
ограничивайте список хостов:

```properties
balancer.discovery.enabled=true
balancer.discovery.hosts=127.0.0.1,192.168.1.10
balancer.discovery.port-start=9000
balancer.discovery.port-end=9100

# Явный список базовых URL; можно комбинировать с hosts/ports
balancer.discovery.urls=http://10.0.0.1:9001,http://10.0.0.2:9001
```

За один проход сканируется не более 500 портов на каждый хост. Discovery
только добавляет новые серверы и не удаляет те, которые перестали отвечать.
Удаление и отключение выполняются через `/api/servers`. Рекомендуется
использовать discovery только в доверенной сети.

## Персистентность и логи

### Подключения серверов

Настройки подключённых серверов сохраняются в:

```text
adaptive-query-balancer/data/connected-servers.json
```

Файл содержит версию формата, счётчик `nextSequence` и список серверов с их
настройками. Запись выполняется после каждого добавления, изменения или
удаления. При старте балансировщик читает файл и восстанавливает подключения.

- По умолчанию путь относительный (`./data/connected-servers.json`); для
  внешнего каталога используйте `BALANCER_SERVERS_FILE` с абсолютным путём.
- Файл исключён из Git через `.gitignore`; предзаполненного файла в поставке
  нет.
- Некорректные записи пропускаются с предупреждением в лог.
- Если файл повреждён полностью, балансировщик стартует с пустым реестром.
- Профиль/URL/заголовки сохраняются, а секреты лучше задавать через `env:VAR`,
  а не записывать в JSON.
- Для чистого старта без сохранённых подключений остановите балансировщик и
  удалите файл (предварительно сохранив его копию, если она нужна).

Статистика запросов, метрики и Beta-оценки стратегий не сохраняются и
сбрасываются при перезапуске процесса.

### Логи

| Компонент | Куда пишется |
|---|---|
| Балансировщик | `.demo/logs/balancer.log` при запуске через `start-demo.sh`; иначе stdout |
| Бекенды | `backends/logs/server-1.log` … `server-5.log` |
| Клиенты | `clients/logs/client-1.log` … `client-3.log` |
| PID-файлы | `.demo/balancer.pid`, `backends/.pids`, `clients/.pids` |

Просмотр в реальном времени:

```bash
tail -f backends/logs/server-4.log
tail -f clients/logs/client-3.log
```

Балансировщик пишет через SLF4J изменения active set, переходы уровня нагрузки и
смену доступности серверов. Бекенды по умолчанию логируют каждый запрос; при
высокой нагрузке логи могут быстро расти, поэтому для длительных прогонов имеет
смысл отключить `backend.log-requests`.

## Сценарии демонстрации

### Scale-out и scale-in

```bash
curl -s -X POST http://localhost:8080/api/monitor/reset
clients/client-1/run.sh --duration 20
```

Низкая нагрузка обычно удерживает в ротации один сервер. Затем запустите более
интенсивный клиент:

```bash
clients/client-2/run.sh --duration 60
```

В интерфейсе наблюдайте рост `activeServers` и `totalCapacity`. После
завершения нагрузки утилизация падает; через cooldown 15 секунд свободные
серверы возвращаются в `STANDBY`.

### Фазовый переход

Сделайте хвост задержек тяжёлым на всех узлах:

```bash
for port in 9001 9002 9003 9004 9005; do
  curl -s -X PUT "http://127.0.0.1:$port/admin/profile" \
    -H 'Content-Type: application/json' \
    -d '{"alpha":1.5,"failureRate":0}' >/dev/null
done
```

Сбросьте метрики и создайте нагрузку:

```bash
curl -s -X POST http://localhost:8080/api/monitor/reset
clients/client-2/run.sh --duration 90
```

На вкладке «Мониторинг» должны измениться `estimatedAlpha`, `smoothedAlpha`,
`EWS`, `CUSUM` и фаза. При переходе в `HEAVY_TAIL` или `WARNING` политика
перестаёт разрешать `EXACT`, и распределение стратегий смещается в сторону
`UNIFORM` и `STRATIFIED`.

Вернуть исходные профили можно перезапуском бекендов:

```bash
backends/stop-all.sh
backends/start-all.sh
```

### Перегрузка и shedding

```bash
curl -s -X POST http://localhost:8080/api/monitor/reset
clients/client-3/run.sh --duration 60
```

Наблюдайте:

- `loadLevel = OVERLOAD`;
- рост `shedCount` и `failedCount`;
- ответы `429` у клиента в поле `shed`;
- записи `REJECTED` в логах бекендов при переполнении их очередей.

Если нужно увидеть именно отсечение балансировщиком, оставьте один активный
сервер с небольшой ёмкостью и подайте нагрузку выше
`capacity × overload-factor`.

### Проверка отказа узла

Смоделируйте отказ на одном бекенде:

```bash
curl -X PUT http://127.0.0.1:9004/admin/profile \
  -H "Content-Type: application/json" \
  -d '{"failureRate":0.5}'
```

Запросы, попавшие на этот узел, начнут возвращать `503`, а клиент увидит их
как `failed`. Балансировщик не повторяет такие запросы на другом сервере.
Для проверки именно health-check остановите процесс узла и дождитесь
следующего цикла проверки (до 15 секунд): сервер будет исключён из активного
набора.

## Частые проблемы

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Интерфейс открывается, но метрик нет | нет клиентов или поток SSE не подключился | запущены ли клиенты, вкладка Network в браузере, `/api/monitor/snapshot` |
| `503 NO_SERVERS` | нет включённых/доступных серверов или открыт circuit breaker | добавлены ли серверы, `/health` бэкендов, `balancer.discovery.enabled`, статус в разделе «Серверы» |
| Много `429 SHED` | нагрузка превышает ёмкость активного набора | `loadLevel`, `shedCount`, число активных серверов, `overload-factor` |
| Много `502 FAILED` | бекенд перегружен, вернул ошибку или не отвечает | `backends/logs/server-*.log`, `/stats` проблемного узла, `failureRate` |
| Активных серверов всегда один | нагрузка ниже порога scale-out | `utilization`, `inFlight`, `scale-out-utilization` |
| Фаза долго `UNKNOWN` | недостаточно успешных задержек | накопите больше запросов, проверьте `windowSize` и ошибки бекендов |
| α не меняется после смены профиля | старые задержки всё ещё в окне | вызовите `/api/monitor/reset` и повторите нагрузку |
| Подключения не восстанавливаются | файл не сохранён или путь отличается | права на `data/`, рабочая директория процесса, `balancer.servers-file` |
| Порт занят | другой процесс уже слушает порт | `ss -ltnp` или `lsof -i :8080`; поменяйте `server.port` |

## Ограничения и особенности

- Бекенды моделируют аналитический движок и железо, а не используют реальную
  БД, Spark или Presto. Набор данных одинаковый и хранится в памяти.
- Запросы не повторяются автоматически. Ошибка бекенда возвращается клиенту
  как `FAILED`.
- Admin-API защищён токеном или loopback-политикой, но клиентский API не имеет
  аутентификации; TLS-терминацию и rate limiting рекомендуется выполнять на
  внешнем прокси/API gateway.
- Метрики, скользящее окно, состояние детектора и Beta-оценки стратегий
  хранятся в памяти и теряются при перезапуске.
- `/api/monitor/reset` не очищает Beta-оценки стратегий: сбрасываются только
  счётчики, окно задержек, детектор фаз, admission control, active set и
  серверная статистика.
- Discovery только добавляет серверы. Если узел исчез, его нужно отключить или
  удалить вручную.
- Health-check считает сервер доступным только по `2xx`; `404`/`401` больше не
  маскируются под здоровье.
- Ошибка выполнения на бекенде (включая его `429` из-за переполнения очереди)
  по-прежнему превращается в `502 FAILED`: автоматические retry не выполняются.
  После 5 подряд ошибок сервер временно исключается из маршрутизации на 30
  секунд (базовый circuit breaker).
- Если бекенд не возвращает `relativeError`/`exactResult` и не помечает ответ
  как точный, accuracy неизвестна: обучение оптимизирует только задержку.
- Контекст Thompson Sampling в текущей реализации группируется только по
  диапазону α. Остальные поля контекста вычисляются, но не разделяют
  Beta-оценки.
- Размер окна, минимальное число выборок, пороги детектора и веса reward теперь
  задаются через `balancer.adaptive.*`; для demo-симулятора используется
  синтетический fallback-набор, а не эталонный CSV.
- Клиенты создают приблизительную нагрузку: темп задаётся паузами между
  запросами и не компенсирует время ответа бекенда.
- Веб-интерфейс является средством демонстрации и мониторинга, а не
  полноценной административной панелью.
